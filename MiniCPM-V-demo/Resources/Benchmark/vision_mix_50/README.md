# vision_mix_50 —— 手机端图文混合集

生成日期：2026-10-20。**50 条**，一条 case = 一张图 + 一句文本；全部单轮、单图。
前 25 条是已经过人工/官方 show case 核对的回归 case，后 25 条是按手机端常见负载补的短问答。

## 组成

| key | 来源 | 条数 | 说明 |
|---|---|---:|---|
| 1–7 | `1B_cases` | 7 | 1B 实测通过：营养表、比萨斜塔、日食、月面、便签、咖啡价、营业时间 |
| 8–19 | `35BA3B_cases` | 12 | 35B-A3B 实测：城市天际线、手写表、月相×3、正四面体、Minard、敦煌票价、板书、拍照解题、手写 markdown、小票 |
| 20–25 | 4.6 show case | 6 | 红吸管折射、登机牌 JSON、菜单加法、饮料翻译、A→C 路径、航班号/日期 JSON |
| 26–50 | 自造补充 | 25 | 识图 5、描述 6、对话 3、OCR/简单数学 8、图表 2、逻辑 1（详见 labels） |

**已审核 case 保持原 prompt 与人工核对答案**，包括少数本来就偏长的推导/表格/总结题（key 13、16、18、19）。
它们放在最前面，用于回归；如果只想要“短答”，可以直接从 key 26 开始跑，或后续再做一份 concise 变体。

| 类型 | keys | 例子 |

补充集的 prompt 都显式限制输出：`只回答…`、`用一句话（不超过 30 字）`、
`只给结果和一行算式`、`Answer with one letter only`。目标是让输出落在
**几个 token 到一两句话**，而不是长篇推理。

## labels.jsonl

App 不读这个文件，只用它做事后分析。每行字段：

```json
{"key":3026,"image":"cat.png","category":"recognition","language":"zh",
 "reviewed":false,"source":"self","source_id":"self#cat-recognition",
 "reference":"猫（cat）。","max_answer_tokens":8,"notes":"..."}
```

- `reviewed`：前 25 条为 true。
- `reference`：参考答案；描述/对话类不是逐字评分标准，只用于人工比对。
- `max_answer_tokens`：期望输出上限的粗略估计，方便筛“短答/长答”。

## 图片与口径

- 图片全部扁平放在本目录，`cases.jsonl` 的 `image` 直接写文件名；
  部署时 `cases.jsonl` 和图片必须同级，不要放子目录。
- 30 张唯一图片，约 17.7 MiB（`du` 约 36M，主要是 6000×4000 的天际线和菜单原图）。
- 同一张图会被不同 case 复用（例如月相 3 条、营养表 3 条）；这是刻意保留的真实用法，
  但跑批时图像编码可能命中缓存，分析 TTFT 时应按图分组看。
- **没有** MMMU 的大学科长篇多选题；原 `mmmu_qa_100` 仍保留，作为可选的硬题 track。
